### Recently completed / merged (newest first)

**PR #71 — Tap-to-interrupt TTS v1.** While Scout is speaking, or still in the 220–650ms pre-TTS "natural pause" delay before speech actually reaches the TTS engine, a screen tap now interrupts him. Went through 3 independent-review rounds before merge (all real, confirmed bugs, all fixed): (1) a pending pre-dispatch cancellation could wrongly clear global speaking state belonging to a *different*, still-genuinely-audible dispatch (the boot announcement + STT-unavailable `QUEUE_ADD` follow-up can coexist); (2) `onStop()` needed to distinguish an actual user tap from a possible internal `QUEUE_FLUSH`-caused stop, via an id-scoped target, not a bare boolean; (3) "submitted to the TTS engine" and "actually audible" are not the same thing with `QUEUE_ADD` — ownership now tracks `onStart()`'s own confirmed id as ground truth, falling back to "submitted" only in the narrow gap before `onStart()` arrives. Cancels pending pre-dispatch speech, stops currently-audible TTS, does **not** close/reset the conversation, does **not** immediately drain a queued `pendingAiAnswer` after a user interruption (a later natural completion still drains it normally), and a tap interrupting the startup greeting still counts as that greeting finishing for PR #68's quiet-period anchor. 22 pure tests, all passing locally. **Needs real-device validation on both Fold 7 and A32 — see below, including whether Samsung/OEM TTS reliably delivers `onStop()`.**

**PR #70 — TinyLlama benchmark screen scrolling.** The benchmark page is now one vertically scrollable page instead of only a cramped, small nested results box — real problem on the A32's smaller screen, made worse by PR #69 raising the run count from 24 to 28. Structural layout fix only (removed the inner results-only `ScrollView`, wrapped the whole page in one outer one) — no benchmark logic, config, prompt, or native-code change. A pre-existing, unrelated Fold/unfold Activity-recreation data-loss risk was found during the investigation and deliberately parked, not fixed here.

**PR #69 — TinyLlama benchmark instrumentation.** Fixed a native timing-fallback bug that could report `prefill=0ms`/`0.0 tok/s` (a fallback condition was trusting a token count as a proxy for timing validity instead of the actual llama.cpp timing value). Added a true `PRODUCTION_DEFAULT` benchmark configuration (`n_threads=2`, `n_threads_batch` left at whatever llama.cpp itself defaults to) — previously **no existing benchmark combo actually matched real production thread behavior**, since all six explicit 2/2–6/6 configs override `n_threads_batch` explicitly. Instrumentation/benchmark-only — `nativeGenerate()`'s own production parameters, `n_ctx`, `n_batch`, `nPredict`, the model, prompt construction, and conversation history are all untouched.

**PR #68 — Post-boot Companion Moment quiet period.** Scout could speak a spontaneous Companion Moment (a personal memory, a curiosity/environment/observation remark) almost immediately after his own boot greeting — every other gate (the 45-minute shared proactive cooldown, the 30s poll throttle) reads as freshly-reset/inert on a cold boot. New dedicated 5-minute Companion-Moments-only quiet period, anchored specifically to the actual face-triggered "Hello. I am Scout."/"I see `<name>`." greeting's own TTS completion — not whichever utterance happens to finish first (that's often `ScoutBootStatus`'s separate, earlier boot-status announcement). Went through 3 review rounds fixing real bugs along the way (a missing import; the wrong anchor event; a pre-greeting window where Companion Moments could still fire before the greeting had ever completed). Scope is Companion Moments only — Companion Memory eligibility, presence idle-silence/return-greeting behavior, the shared 45-minute cooldown, and user-initiated conversation are all untouched.

**PR #67 — Busy-Brain filler delay 2s → 5s.** The "Let me think about that" filler now waits 5 seconds (was ~2s) before speaking, still only if the generation is genuinely still pending by then. Real-device feedback: substantially less annoying; a fast answer now usually arrives before any filler is ever spoken.

**PR #66 — Vision label-whitelist fix.** `keepVisionLabel()`'s deny-list was unconditionally deleting 6 labels (`glasses`, `hat`, `cap`, `shirt`, `jacket`, `coat`) that `OBJECT_WHITELIST` already explicitly allowed later in the same pipeline — traced from a real report of prescription glasses being described as "sunglasses." One-line-scope fix; the other 15 face-attribute deny-list entries, `OBJECT_WHITELIST` itself, and ML Kit configuration are untouched.

**PR #65 — Settings Memory Export/Import marked "coming in a future release."** Reverts PR #64's Settings-side export wiring (below) — full export/import (restore, People/embedding handling, HabitLayer reconciliation, rollback, versioning) was investigated in depth and deliberately deferred past this release for stability. Both Settings rows now honestly say "Coming in a future release" instead of either performing a real export or showing stale "coming soon" wording. The voice **"export brain"** command path is untouched and still works.

**PR #64 — (superseded by PR #65, three hours later) Settings Memory Export wiring.** Briefly wired the Settings "Memory Export" row to the existing `ScoutExportManager` (the same export the voice command already used) instead of a toast. Reverted same-day by PR #65 once full export/import was deferred — recorded here only for an accurate history; the Settings row does not currently perform a real export.

**PR #63 — TTS caption UI-thread safety.** `TextToSpeech.UtteranceProgressListener` callbacks aren't guaranteed to run on the main thread, but `speak()` mutates the closed-captions `TextView` directly and is called from both main-thread paths and those callback threads — risking `CalledFromWrongThreadException`. Fix wraps only the three-line caption-update body in `runOnUiThread{}`, the same marshaling pattern already used elsewhere in the file. This was the leading candidate root cause for PR #52's "reply displays but is sometimes never spoken" watch item — **confirmed merged, but not yet confirmed fixed on a real device.**

### TinyLlama Performance Findings (verified architecture)

- **Load path:** the model loads with `nCtx = 512`, `nThreads = 2`.
- **Actual generation path:** every single generation destroys and recreates a fresh llama context with `n_ctx = 2048`, `n_batch = 512`, `n_threads = 2`, `n_threads_batch` left at whatever llama.cpp itself defaults to. No cross-request KV-cache/context reuse exists today. Production `nPredict = 100`.
- **Important:** the load-time `nCtx = 512` does **not** describe the context actually used for production generation — do not describe production as simply "n_ctx=512" anywhere.

### TinyLlama Benchmark Status

- **Galaxy Fold 7:** a previous benchmark run showed strong sensitivity to thread configuration; the approximate overall best was around 5/5, and 6/6 was **not** automatically faster than 5/5 — "more threads = faster" is not a safe assumption.
- **Galaxy A32:** partial benchmark evidence also showed meaningful thread sensitivity, but the dataset is incomplete — **no winning configuration has been declared.**
- PR #69 changed the benchmark itself (added `PRODUCTION_DEFAULT`, fixed a real timing-instrumentation bug) — **both devices need a fresh benchmark run on current code** before any production thread-count change is even considered. **No production TinyLlama performance tuning has been approved.**

## 3. Scout's Core Philosophy

Scout should feel: Calm. Thoughtful. Quietly alive. Emotionally subtle. Occasionally curious.
Scout should NOT feel: Excited. Scripted. Fake. Cartoonish. Hyperactive. Constantly praising.

**Stability > Features | Presence > Intelligence | Honest > Fake cheerful | Local-first > Cloud | Predictable > Flashy**
